The Mailhouse plugin: free, for every site

One plugin for the whole path an email takes: getting it off the server reliably, and running the site’s own newsletter. It replaces a separate SMTP plugin and a separate newsletter plugin, and it works on its own, with or without Central.

One dashboard, many sites, each still in charge

Every site runs the Mailhouse plugin and carries on working on its own. Mailhouse Central joins them up without taking their lists away from them.

Each site owns

  • Its subscribers: addresses, names, fields and status
  • Consent, recorded per site with its dates
  • Its tags and who has them
  • Its mail settings and passwords, which never leave it

The centre owns

  • Who is the same person across sites
  • Mailing lists and saved segments, which can span sites
  • Campaigns: their content, schedule and audience
  • Central sending accounts, for mail sent from the centre

Every record has exactly one writer. An edit made in the dashboard is a request to the site, and the centre’s copy changes when the site reports back.

So there’s nothing to settle by guesswork. If a site and the centre both want to change a subscriber’s name, the centre asks and the site does it.

What Mailhouse Central does

Everything below is built and running at app.mailhousecentral.com.

  • One directory of everybodyEvery subscriber of every connected site in one place: search and filter by site, status, tag or date, and open a person to see each of their subscriptions separately.
  • Lists, tags and segmentsLists that span sites, tags managed on every site at once, and segments as saved filters with a preview of who they find on each site.
  • Changes as requestsOnce you allow it for a site, edit, unsubscribe, remove or add subscribers from the dashboard. The site carries out each change under its own rules and reports back.
  • Import, export and erasureImport a file into a site, export any filter, mark an address “do not contact”, or erase a person from the centre and from every site that holds them.
  • Campaigns written onceA visual editor or HTML, with merge tags. Previews show each site’s own header, footer and colours. Somebody on two sites gets it once unless you say otherwise.
  • Sent through each siteEach site is handed the campaign as a signed request and sends it in its own template, through its own mail settings, to those still subscribed at that moment.
  • Or sent from the centreAdd accounts with Postmark, Resend, SendGrid, Amazon SES, MailChannels, Bird, Microsoft 365 or any mail server, check sender addresses against SPF, DKIM and DMARC, and choose that route for a site.
  • Hold, resume, call offCampaigns can be tried out with a test send first, then held, let go or cancelled per site while they run.
  • Delivery reports and analyticsAccepted, delivered, bounced and complained, per campaign and site beside site. A figure a route can’t supply says “not available”, never zero.
  • Sign-in that takes security seriouslyA second factor with recovery codes, passwords checked against a breached-password list, four roles, and an append-only audit log.

Connecting a site

No password is typed into anything and no long-lived secret is ever emailed. The site makes its own key and keeps it.

  1. Add the website

    Give it a name and its address under Websites, Add website, in Central.

  2. Copy the enrolment token

    It’s shown once, and it expires.

  3. Paste it into the site

    On the site, an administrator pastes the token and the centre’s address under Mailhouse, Settings, Central. This needs Mailhouse 1.7.0 or later.

  4. The site registers itself

    It generates a key pair, keeps the private half encrypted, and sends the public half to the centre with the token, which is then used up.

  5. It copies its list across

    The site sends the list it already has, then every change about a minute after it happens. Once a day the two are compared and the centre’s copy is put right.

Read-only until you say so

A newly connected site can be seen from Central but not changed. An administrator allows changes per site, and a site can refuse them outright with one line in wp-config.php.

A copied site switches itself off

Each registration is tied to the site’s address. A staging copy running somewhere else notices the mismatch and disables its own connection, so it can’t report as the live site or send its campaigns.

Rules it’s built not to break

They hold for every site, every campaign and every person on a list, and each one is tested.

Consent belongs to each site

Being subscribed on one site says nothing about another. Merging two sites’ records into one person never merges their consent.

No one is resubscribed from the centre

Nothing in the dashboard can move an unsubscribed or bounced address back to subscribed. Only the person can, from a link their site sends.

The site has the last word

Whatever recipient list the centre sends, the site checks each person again at the moment of sending. Someone who unsubscribed a minute ago is skipped.

Unclear sends aren’t resent

If a send is cut off and nobody can tell whether it went, it’s marked uncertain and waits for a person to decide. Nobody gets the same newsletter twice by accident.

Secrets stay where they are

A site’s mail passwords and its subscribers’ private links never leave the site. Content from the centre is plain data, never code the site would run.

Sites call the centre, not the other way round

Each site sends its changes and collects its instructions. A site that’s down, slow or behind a firewall affects only itself.

When something breaks

How the system behaves. Each case has its own test.

If this happensThen
The centre goes downSites keep taking signups, unsubscribes and sending. Changes queue up on each site and arrive in order when it’s back.
One site goes downOnly its own campaigns pause. Every other site carries on.
The connection drops mid-requestThe sender tries again, and the other side recognises a repeat and doesn’t apply it twice.
A worker dies mid-sendThe message is marked uncertain, never resent automatically.
The job queue is wipedJobs are rebuilt from the database, which is the only source of truth.
A site is restored from an old backupThe centre notices it has gone back in time and checks every subscriber with it before accepting new changes.
A mail provider sends the same report five timesIt’s counted once.

Questions

Can I use it now?

The plugin, yes: download it and install it on any WordPress site. Mailhouse Central has been live since November 2026 with its first sites connected, and it opens to more as prices are set.

What will it cost?

The Mailhouse plugin is free and stays free, including the part that connects a site to Central. Mailhouse Central is a paid service. Prices aren’t set yet; they’ll be published before it opens to everyone.

How does the plugin stay up to date?

It checks its own GitHub releases twice a day, as WordPress does for any plugin. A new version shows on the Plugins screen and installs with one click, or by itself if you turn on auto-updates. Only signed releases install.

Does a site need the centre to keep working?

No. A connected site keeps taking signups, confirming, unsubscribing and sending its own newsletters whether or not the centre is reachable. A site that isn’t connected runs exactly as it does without Central.

What if the same person is on several sites’ lists?

The dashboard shows them as one person with a separate subscription on each site. A campaign sent to several sites mails them once by default, or once per site if you choose.

Will newsletters still look like they come from each site?

Yes. The centre writes the body; each site’s campaign goes out in that site’s own template, with its own logo, colours and unsubscribe link.

Can I send through each site’s existing mail setup?

Yes, that’s the default: a site sends Central’s campaigns through its own mail settings. Or an administrator can choose a sending account held at the centre for a site, and its campaigns then go out from there, still in the site’s own template.
