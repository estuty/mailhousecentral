Every site’s newsletter, run from one place.

Mailhouse Central is one dashboard for the newsletters of many WordPress sites. Each site keeps its own subscribers and the final say over who it mails. The centre is where you see them, organise them and write to them.

One dashboard, many sites, each still in charge

Every site runs the Mailhouse plugin and carries on working on its own. Mailhouse Central joins them up without taking their lists away from them.

Each site owns

  • Its subscribers: addresses, names, fields and status
  • Consent, recorded per site with its dates
  • Its tags and who has them
  • Its mail settings and passwords, which never leave it

The centre owns

  • Who is the same person across sites
  • Mailing lists and saved segments, which can span sites
  • Campaigns: their content, schedule and audience
  • Central sending accounts, for mail sent from the centre

Every record has exactly one writer. An edit made in the dashboard is a request to the site, and the centre’s copy changes when the site reports back.

So there’s nothing to settle by guesswork. If a site and the centre both want to change a subscriber’s name, the centre asks and the site does it.

Connecting a site

No password is typed into anything and no long-lived secret is ever emailed. The site makes its own key and keeps it.

  1. Add the website

    Give it a name and its address under Websites, Add website.

  2. Copy the enrolment token

    It’s shown once, and it expires.

  3. Paste it into the site

    An administrator pastes the token and the centre’s address into Mailhouse’s settings. That screen arrives with plugin version 1.7.0.

  4. The site registers itself

    It generates a key pair, keeps the private half encrypted, and sends the public half to the centre with the token, which is then used up.

  5. It reports in

    A signed check-in every minute. The website shows as connected, and as not reporting if it goes quiet for five minutes.

A copied site switches itself off

Each registration is tied to the site’s address. A staging copy running somewhere else notices the mismatch and disables its own connection, so it can’t report as the live site or send its campaigns.

Quiet sites still keep time

WordPress only runs its schedule when someone visits. Once a minute the centre visits each connected site’s wp-cron.php, an empty request, so a site with no traffic still sends on time. It only ever calls public https addresses.

Rules it’s built not to break

These are the design’s ground rules. They hold for every site, every campaign and every person on a list.

Consent belongs to each site

Being subscribed on one site says nothing about another. Merging two sites’ records into one person never merges their consent.

No one is resubscribed from the centre

Nothing in the dashboard can move an unsubscribed or bounced address back to subscribed. Only the person can, from a link their site sends.

The site has the last word

Whatever recipient list the centre sends, the site checks each person again at the moment of sending. Someone who unsubscribed a minute ago is skipped.

Unclear sends aren’t resent

If a send is cut off and nobody can tell whether it went, it’s marked uncertain and waits for a person to decide. Nobody gets the same newsletter twice by accident.

Secrets stay where they are

A site’s mail passwords and its subscribers’ private links never leave the site. Content from the centre is plain data, never code the site would run.

Sites call the centre, not the other way round

Each site sends its changes and collects its instructions. A site that’s down, slow or behind a firewall affects only itself.

When something breaks

How the system is designed to behave. Each case gets its own test in the milestone that builds it.

If this happensThen
The centre goes downSites keep taking signups, unsubscribes and sending. Changes queue up on each site and arrive in order when it’s back.
One site goes downOnly its own campaigns pause. Every other site carries on.
The connection drops mid-requestThe sender tries again, and the other side recognises a repeat and doesn’t apply it twice.
A worker dies mid-sendThe message is marked uncertain, never resent automatically.
The job queue is wipedJobs are rebuilt from the database, which is the only source of truth.
A site is restored from an old backupThe centre notices it has gone back in time and checks every subscriber with it before accepting new changes.
A mail provider sends the same report five timesIt’s counted once.

Built in small milestones, each checked against written acceptance criteria before the next one starts. Nothing has been deployed yet.

  1. Built

  2. Built

    The central application’s foundation

    The database with each site’s rows walled off from every other’s, sign-in with a second factor and roles, the dashboard shell, and websites that register and report in.

  3. Next

    Plugin 1.7.0. Sites connect from their own settings screen, send their changes up, and bring their whole list across, resumably.

  4. Planned

    One directory across every site, with each site’s subscription shown separately. Edits as signed requests to the site, plus lists, tags, segments, import and export.

  5. Planned

    Campaigns

    A central editor, per-site previews in each site’s own design, and targeting across sites that mails each person once.

  6. Planned

    Sending through each site

    Plugin 1.9.0. Campaigns go out through the site’s own mail settings, in its own template, with live progress in the dashboard.

  7. Planned

    Sending from the centre

    Central provider accounts, with rate limits, bounce and complaint reports, and unsubscribes passed back to the site.

  8. Planned

  9. Planned

What works today

  • Signing inPasswords checked against a breached-password list held on the server, a second factor with recovery codes, and owners and admins required to set one up before their powers apply.
  • Roles and an audit logFour roles, decided in one place, with every sensitive action recorded and append-only.
  • WebsitesAdd, rename, pause, disconnect and remove sites; issue enrolment tokens; revoke a site’s key.
  • Signed check-insA site’s requests are refused unless its signature is right, and every way of getting it wrong is tested.
  • Sites kept apartThe database itself hides every other site’s rows from a request made on behalf of one site.

Built on

  • Next.js and TypeScriptThe dashboard and its API
  • A separate workerEverything in the background, so a dashboard restart never interrupts sending
  • PostgreSQLWhere everything lasting is kept
  • RedisScheduling only; nothing it holds can’t be rebuilt
  • Ed25519 signaturesOne key pair per site; the centre keeps only the public half
  • Docker Compose behind CaddyOn one server, with automatic certificates

Questions

Can I use it yet?

Not on real sites. The foundation is built and runs on a local test setup with two WordPress sites. Connecting a site from its own settings arrives with the connector, the next milestone, and nothing will be deployed until production hardening is done.

What will it cost?

The Mailhouse plugin is free and stays free, including the part that connects a site to Central. Mailhouse Central will be a paid service. Prices aren’t set yet; they’ll be published before it launches.

Does a site need the centre to keep working?

No. A connected site keeps taking signups, confirming, unsubscribing and sending its own newsletters whether or not the centre is reachable. A site that isn’t connected runs exactly as it does today.

What if the same person is on several sites’ lists?

The dashboard shows them as one person with a separate subscription on each site. A campaign sent to several sites mails them once by default, from the first site in the campaign, or once per site if you choose.

Will newsletters still look like they come from each site?

Yes. The centre writes the body; each site wraps it in its own template, with its own logo, colours and unsubscribe link.

Can I send through each site’s existing mail setup?

That’s one of the two planned routes. A campaign can go out through each site’s own mail settings, or through a sending account held centrally. The route is chosen per site per campaign and never switches by itself.
