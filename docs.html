Mailhouse admin guide#

Everything here is done from the WordPress admin. No code.

1. Make email leave the site#

Mailhouse → Settings → Delivery.

WordPress out of the box hands mail to PHP's mail(). Nothing about that message is authenticated, so Gmail, Outlook and everyone else treat it as suspicious. This is the one setting that matters most.

Who it comes from#

Field What to put
From address An address at your own domain. Not Gmail, not Yahoo — you cannot prove you are allowed to send as them, and it will be rejected.
From name Whatever a reader should see. Usually the site name.
Force on every email On, unless a shop or form plugin needs to send as somebody else.
Default Reply-To Where replies should land, if the From address is nobody's mailbox.
Send bounces back to the From address Leave on. Otherwise bounces go to the web server, where nobody reads them.

The transport#

Pick one and fill in its fields:

  • SMTP server — works with Google Workspace, Microsoft 365, Fastmail, your host, or a transactional service that also offers SMTP. Port 587 with STARTTLS is the usual answer; 465 means SSL/TLS. Quick setup fills in the server for Gmail, Microsoft 365, Outlook.com, Zoho, Yahoo, iCloud, Amazon SES and Hostinger.
  • SendGrid / Mailgun / Brevo / Postmark / Resend / Amazon SES / Mailjet / SparkPost / SMTP2GO / Elastic Email / MailerSend / Zoho ZeptoMail / Mailchimp Transactional (Mandrill) — create an API key with send permission only, and verify your sending domain in their dashboard first. The API is generally faster and more informative when something goes wrong than SMTP is.
  • PHP mail — the default. Change it.

Under Backup and newsletter transport you can also pick a second transport that takes over when the main one refuses a message, and a separate transport for newsletters, so a spam complaint about bulk mail cannot drag down password resets and receipts.

Then go to Tools → Send a test email. It tells you what the transport said, not just whether it worked.

Keeping credentials out of the database. Anything you type in a password field is encrypted before it is stored. If the database is backed up somewhere you do not fully control, put the secret in wp-config.php instead:

define( 'MAILHOUSE_SMTP_PASS', 'the-password' );

The field then says so and is ignored. The other constants are MAILHOUSE_SENDGRID_KEY, MAILHOUSE_MAILGUN_KEY, MAILHOUSE_BREVO_KEY, MAILHOUSE_POSTMARK_TOKEN, MAILHOUSE_RESEND_KEY, MAILHOUSE_SES_SECRET_KEY, MAILHOUSE_MAILJET_SECRET, MAILHOUSE_SPARKPOST_KEY, MAILHOUSE_SMTP2GO_KEY, MAILHOUSE_ELASTICEMAIL_KEY, MAILHOUSE_MAILERSEND_KEY, MAILHOUSE_ZEPTOMAIL_TOKEN and MAILHOUSE_MANDRILL_KEY.

Email design#

Settings → Email design sets the look of every email: logo, header colour, brand and button colours, footer text, postal address and social links. With Use this design for all email the site sends on (the default), WordPress's own messages and other plugins' simple emails get the same header and footer. Emails that arrive as a complete designed page, such as most shop receipts, are left alone. Open a preview shows the saved design; Send me a test mails it to you.

Matching the site#

If your theme declares its colours — any block theme with a theme.json does — the Colours section shows them and offers Use my theme's colours. One click copies the brand, page, message, header and text colours across, and each stays editable afterwards. A brand new install picks them up on its own.

There are two colours worth understanding if your site is dark:

Setting What it is
Page background Behind the message, like the wall.
Message background The card the message sits on. Keep it a shade apart from the page, or the card stops looking like a card.
Text colour Headings and body text. On a dark message background, pick a light one.

Mailhouse works out the rest: the footer, quote and code colours, the border, and whether button text should be black or white.

A light design also gets a dark-mode variant for readers whose phone is in dark mode. A design that is already dark does not — overriding it would swap your colours for somebody else's greys.

These colours are not only for the email. The confirmation popup and the unsubscribe and preferences pages take them too, so somebody clicking a link in your newsletter stays in your colours the whole way. Before 1.5.0 those two pages used only the brand colour and were otherwise white, which showed up on a dark design as a white page at the end of a dark email.

A theme with no theme.json (most older themes) cannot be read, and the panel says so rather than applying a generic palette and calling it yours.

New post notifications#

Under Emails there is a New post notification, created switched off. Publish it to turn notifications on. In its settings you choose:

  • which post types and categories trigger it;
  • one email per post, or a daily or weekly digest at a set hour;
  • whether it sends automatically, or is saved as a draft and you get an email asking you to review and send it.

The notification goes out two minutes after a post is published, so a typo fixed straight away is fixed in the email too. Password-protected posts are never sent, and authors can tick Don't email subscribers about this post in the editor sidebar. Use {{post_card}} for a ready-made card with the image, title, excerpt and a Read more button, and {{post_list}} in a digest.

Making it actually arrive#

The plugin cannot do this part for you. At your DNS host, for the domain you send from:

  1. SPF — one TXT record listing who may send as you. Your provider gives you the exact value.
  2. DKIM — the provider gives you a record; it signs your mail.
  3. DMARC — a TXT record at _dmarc.yourdomain.com. Start with v=DMARC1; p=none; rua=mailto:you@yourdomain.com and tighten it later.

Without these, good delivery is luck.

2. Watch what happens#

Mailhouse → Email log.

Every message and its outcome. When somebody says "I never got the reset email", this is where the answer is: sent, or failed with the reason the transport gave.

  • Delivered means the transport accepted it, not that it reached an inbox. A message can still bounce or be filtered afterwards.
  • Failed shows the error. "Could not instantiate mail function" means PHP mail() is not working — set up a real transport. "550 …" or "Invalid API key" comes straight from the provider.

Under Settings → Log & alerts you can keep entries for a chosen number of days, and be emailed when delivery starts failing (at most once an hour, so a broken transport cannot flood you).

Save message content is off deliberately. With it on you can resend from the log, but password reset links and order details then sit in the database until the retention window passes. Turn it on while debugging; turn it off after.

Bounces and complaints#

A bounce does not happen while you are sending. It arrives at your provider minutes or days later, and they are the only one who knows. So they have to tell you — and then Mailhouse can retire dead addresses without anybody reading a mailbox.

Sending to addresses that no longer exist is the fastest way to ruin a domain's reputation, so this is worth ten minutes of setup.

Settings → Log & alerts → Bounces and complaints. Copy the endpoint shown for your transport and paste it into the provider:

Provider Where Events to send
SendGrid Settings → Mail Settings → Event Webhook Bounced, Dropped, Spam Reports, Unsubscribed, Delivered
Mailgun Sending → Webhooks Permanent Failure, Temporary Failure, Complained, Unsubscribed, Delivered
Brevo Transactional → Settings → Webhooks Hard bounce, Soft bounce, Blocked, Marked as spam, Unsubscribed, Delivered
Postmark Servers → your server → Webhooks Bounce, Spam Complaint, Subscription Change, Delivery
Resend Webhooks → Add email.bounced, email.complained, email.delivered

Send the delivered event too if the provider offers it. It is what clears a soft-bounce count, so a mailbox that was briefly full does not creep towards being retired.

If campaigns go out through their own transport, you will see two endpoints. Set both up: a bounce reported to one provider says nothing about the other, and the newsletter stream is the one bounces matter most on.

The other transports — SES, Mailjet, SparkPost, SMTP2GO, Elastic Email, MailerSend, ZeptoMail, Mailchimp Transactional — can report bounces too, but Mailhouse does not parse their callback formats yet. SMTP and PHP mail have no callbacks at all; that is one of the better arguments for using a mail API.

Then set the signing key. Mailgun, Resend and SendGrid can sign what they send, and the fields are right below the endpoint. Without a signature, the only thing protecting the endpoint is the secret in the URL — and anyone who learns that URL could mark your subscribers as bounced, which is a quiet way of cutting people off your list. Set the key where one exists.

If a URL ever leaks, Replace the key. Every endpoint already saved in a provider dashboard stops working until you paste the new one in, so do it in that order.

What each event does#

What happened What Mailhouse does
Hard bounce — the address does not exist Status becomes Bounced. Anything queued for them is dropped.
Soft bounce — mailbox full, server busy Counted, nothing else. At three (configurable) the address is retired. A confirmed delivery resets the count to zero.
Spam complaint Unsubscribed immediately, whatever their status was. Non-negotiable: continuing after a complaint is what gets a domain blocked outright.
Unsubscribed at the provider Unsubscribed here too.
Opens, clicks, deferrals Ignored. Deferrals are temporary and the provider is still retrying; opens and clicks are tracked here already, if you turned that on.

All of it appears in the email log with the provider's own wording, so "why did this person stop receiving the newsletter" has an answer you can read. Bounced and Spam complaint views appear in the log as soon as there is something in them.

A bounce for somebody who was never a subscriber — a receipt, a password reset — is logged too, but there is no list membership to change.

3. Collect subscribers#

A form#

Paste this into any page, post or widget:

[mailhouse_form]

Or add the Newsletter form block. Both produce the same form.

Useful attributes:

[mailhouse_form title="Stay in touch" description="One email a month." name="first" tags="weekly" layout="inline"]
Attribute Values
title, description, button Any text
name none, first, full
tags Comma separated. Tags that do not exist yet are created.
layout stacked or inline
redirect A URL to send people to after signing up
consent yes or no

Defaults for all of these live under Settings → Signups, so you usually only need the bare shortcode.

You can also offer signup on the comment form and the registration form, under the same tab.

What happens when somebody signs up#

  1. They are stored as pending.
  2. They get the confirmation email. Nothing else is sent until they click.
  3. Clicking makes them subscribed, and the welcome email goes out.
  4. They land on your site with a short message over the top confirming it worked, in your brand colours. It closes with Escape, a click outside, or the button.

Somebody who has just confirmed is as interested as they will ever be, so the site is a better place to leave them than a page with nothing on it. If you would rather they saw a plain confirmation page, switch After someone confirms under Settings → Signups.

Clicking the same link twice — or a mail scanner following it — says the link has already been used, not that something went wrong.

This is double opt-in, and it is on by default. It is what stops a bot — or somebody typing a stranger's address — from putting anyone on your list, and it is most of the difference between a list that reaches inboxes and one that does not.

The form answers with the same message whether the address was new, already subscribed, or a bot tripping the honeypot. That is deliberate: any difference would let a stranger use your form to test who is on your list.

Tags#

Mailhouse → Tags. A flat set of labels. A subscriber can carry any number, and a broadcast can be aimed at one of them instead of everybody. Simpler than separate lists, and nobody ends up stored three times.

4. Send something#

Mailhouse → Emails → Add email.

  • The title is internal. The subject line is what readers see.
  • Preview text is the grey line the inbox shows after the subject. Fill it in; left empty, mail clients pick their own, usually badly.
  • Write the body in the editor. Keep it simple — email clients are not browsers.
  • Merge tags go anywhere in the subject or body. {{first_name|there}} uses "there" when you do not know their name. The full list is in the sidebar while you edit.

Type decides what it is:

Type Behaviour
Broadcast A one-off. You press Send.
New post notification Sent automatically whenever a post is published.
Welcome email Sent once, when somebody joins.
Confirmation email The double opt-in email. Must contain {{confirmation_url}}.

The automations are on when the email is published and off when it is a draft. Editing their wording is just editing the post.

Sending a broadcast#

  1. Publish the email. Publishing does not send it.
  2. In the Sending panel, choose who it goes to.
  3. Send test to yourself first. Always.
  4. Send now, or set a date and time first.

It goes out in batches — 20 a minute by default, adjustable under Settings → Newsletter → Sending. Keep it under whatever your host or provider allows. While it runs you can pause, resume or cancel; anyone who unsubscribes part-way through will not receive it.

Afterwards the email's row shows how many were sent, and opens and clicks if tracking is on.

Scheduled sends need cron. WordPress runs scheduled work when somebody visits the site. On a quiet site that can be late. If your host offers a real cron job, point it at wp-cron.php every minute. The Tools screen tells you whether cron is working.

5. Tracking, and whether to#

Settings → Newsletter → Tracking. Both off by default.

  • Opens works by putting an invisible image in the email that reports back when it loads. Apple Mail loads it whether or not anybody read anything, so treat the number as a rough signal.
  • Clicks works by routing every link through your site first.

Both are real privacy costs. If you turn them on, say so in your privacy policy. Unsubscribe links are never tracked — they have to work regardless.

6. Importing and exporting#

Mailhouse → Tools.

  • From another plugin. Noptin and WP Mail SMTP are detected automatically. Nothing is deleted from them; import, check the result, then deactivate them.
  • From a CSV. The first row must be a header with a column called email. first_name, last_name, status and tags are used if present. Existing addresses are updated, never duplicated.
  • Export gives you everything, including tags and engagement counts.

Only import addresses that asked to hear from you. A bought list is how a sending domain gets blocked, and it is not undoable.

Keeping it up to date#

Mailhouse is not on the wordpress.org directory, so it reports its own updates from its releases on GitHub. There is nothing to set up: a new version appears on Plugins and Dashboard → Updates with its release notes, and installs with one click. WordPress's own "enable auto-updates" toggle works on it like any other plugin.

Nothing about the site is sent anywhere. The check reads a public list of releases and that is all, and it runs on the twice-daily schedule WordPress already uses for every other plugin.

If you would rather not wait for that schedule, the plugin's row on the Plugins screen has a Check for updates link. Tools → Status shows where the last check got to, which is the place to look if an update you are expecting has not appeared.

Coming from a version before 1.4.0? Those had no update mechanism, so that one step is manual. Download the zip from the releases page and upload it under Plugins → Add New → Upload Plugin; WordPress will notice the existing copy and offer to replace it. Your settings, subscribers and log are not touched. Take the mailhouse-<version>.zip file rather than the "Source code" archive — the source archive unpacks to a differently named folder, and WordPress would install it as a second plugin instead of replacing this one.

When something is wrong#

Symptom Look at
Nothing arrives at all Tools → Send a test. The error names the cause.
Mail arrives but goes to spam SPF, DKIM and DMARC on your sending domain.
A campaign is stuck at "Sending" Tools → Status: is cron running?
The confirmation email never comes Email log. It will be there, sent or failed.
Two plugins fighting over delivery The admin warns you by name. Deactivate one.
Somebody stopped receiving the newsletter Subscribers: are they Bounced? The log says why.
Bounces are not being recorded Open the endpoint URL in a browser. It should answer {"ok":true}; anything else means the key is wrong.
No update is showing for a version you know exists Tools → Status, the Updates row. It says whether the last check failed.

Tools → Status has a summary worth copying into any support request.

Moving in from Noptin and WP Mail SMTP#

Both are detected automatically. Nothing is deleted from either — you import, check the result, and only then deactivate them.

Do it in this order. Delivery first: importing a list before mail can leave the site means a queue full of confirmations that cannot be sent.

1. Delivery, from WP Mail SMTP#

Mailhouse → Tools → Move in from another plugin → WP Mail SMTP → Import.

What comes across:

WP Mail SMTP Mailhouse
From address, From name, and their "force" switches The same
Return path Send bounces back to the From address
Mailer: SMTP, SendGrid, Mailgun, Sendinblue, Postmark, PHP mail The matching transport (Sendinblue is Brevo)
SMTP host, port, encryption, auth, username, password The same
API keys, Mailgun domain and region, Postmark stream The same

What does not:

  • Amazon SES, Gmail/Google Workspace OAuth, Outlook OAuth, Zoho, SMTP.com, Sendlayer. Mailhouse has no OAuth transports. For Google Workspace or Microsoft 365, use SMTP with an app password — it is simpler and it does not break when a token expires. For SES, use its SMTP interface.
  • Credentials that live in wp-config.php. Nothing there is copied, because nothing there is in the database. Add the Mailhouse constants instead:
define( 'MAILHOUSE_SMTP_PASS', '...' );
define( 'MAILHOUSE_SENDGRID_KEY', '...' );
define( 'MAILHOUSE_MAILGUN_KEY', '...' );
define( 'MAILHOUSE_BREVO_KEY', '...' );
define( 'MAILHOUSE_POSTMARK_TOKEN', '...' );
define( 'MAILHOUSE_RESEND_KEY', '...' );
  • The old email log. Two schemas, different shapes. Keep WP Mail SMTP installed but deactivated for a while if you need the history, or export it first.

Then: Settings → Delivery, check what arrived, and Tools → Send a test email.

Deactivate WP Mail SMTP#

Only once the test passes. Two plugins both reconfiguring PHPMailer is a coin toss over which one wins, and Mailhouse will warn you in the admin until one of them goes.

2. The list, from Noptin#

Mailhouse → Tools → Move in from another plugin → Noptin → Import.

Noptin's column names have moved between versions, so the importer reads whatever is actually in the table.

Noptin Mailhouse
email email
first_name, second_name first_name, last_name
active = 1 (Noptin stores this inverted) Status unsubscribed
confirmed = 1 Status subscribed
Neither — on the list, never confirmed Status pending
date_created Signup date, preserved
— Everyone gets a Noptin import tag

Nobody is emailed by the import. Not the confirmations, not the welcomes. An import that mails four thousand people is a disaster, so it does not happen.

About the pending ones#

Addresses Noptin never confirmed arrive as pending, which means nothing is sent to them until they confirm. That is the safe reading, and it is the one that protects your sending reputation.

If you are confident they genuinely opted in — a single opt-in form you ran yourself, with records — you can promote them: Subscribers, filter to Pending, select all, Mark as subscribed. Think about it first. A list with unconfirmed addresses on it is how domains get blocked, and that is not undoable.

Alternatively, select them and Resend confirmation to ask properly. Expect most not to answer; the ones who do are worth more than the ones who did not.

What does not come across#

  • Forms. Noptin's form designs do not translate. Replace each one with [mailhouse_form] or the Newsletter form block, then set the defaults under Settings → Signups so you rarely need attributes.
  • Campaigns and automations. Past campaigns and their statistics stay in Noptin. Rewrite the automated emails — there are three, they are short, and the defaults are already written for you under Mailhouse → Emails.
  • Custom fields and Noptin's own tags/lists. These vary too much between versions and add-ons to map reliably. Export what you need to CSV from Noptin first, then import it here; a tags column is honoured.
  • Merge tag syntax. Noptin's [[first_name]] works in Mailhouse unchanged — the double-bracket form is accepted alongside {{first_name}} precisely so pasted content still works.

Unsubscribe links in mail already sent#

Links in emails Noptin already delivered keep pointing at Noptin's endpoints. While Noptin is still installed they keep working. Once it is gone they will not, which is an argument for leaving it installed-but-deactivated for a few weeks, or for sending one issue from Mailhouse — every one of those carries a fresh unsubscribe link and a List-Unsubscribe header.

3. Afterwards#

  1. Subscribers — do the counts look right?
  2. Emails — edit the confirmation and welcome emails so they sound like you.
  3. Sign up through your own form, with a real address, and confirm. End to end.
  4. Emails → Add email, send a test to yourself, then send a small broadcast to a tag with two people on it before you send to everybody.
  5. Tools → Status — cron running, transport configured, no conflicts.
  6. Deactivate Noptin and WP Mail SMTP.

Keep both installed but deactivated for a month. Their tables are still there if something turns out to be missing; deleting a plugin is what removes them.

Coming from something else#

No importer, but a CSV always works: export from the old plugin with at least an email column, and optionally first_name, last_name, status and tags, then Tools → Import subscribers from a CSV. Existing addresses are updated rather than duplicated, so a re-run is harmless.

Mailhouse developer guide#

How delivery is intercepted#

The interesting decision in this plugin is where it takes over wp_mail().

The obvious approach is to short-circuit pre_wp_mail, parse the arguments and build the message yourself. That means re-implementing header parsing, MIME assembly and attachment handling, and it silently breaks every plugin that hooks phpmailer_init expecting to adjust the message.

Instead, Mailhouse hooks pre_wp_mail only to swap the global $phpmailer for a subclass, then returns null so WordPress carries on exactly as usual:

// includes/mail/class-mailhouse-mailer.php
$phpmailer = new Mailhouse_PHPMailer( true );
return null;

Mailhouse_PHPMailer overrides one method. SMTP and PHP mail fall straight through to PHPMailer. An API transport gets the message after preSend() has assembled it:

public function send() {
    $provider = Mailhouse_Mailer::provider();

    if ( ! $provider || ! $provider->is_api() ) {
        return parent::send();
    }

    if ( ! $this->preSend() ) {
        return false;
    }

    return $provider->send( $this );
}

Consequences worth knowing:

  • phpmailer_init, wp_mail_succeeded and wp_mail_failed all fire normally. The log listens to the last two rather than to anything private.
  • A transport reports failure by throwing PHPMailer\PHPMailer\Exception. wp_mail() catches it and turns it into wp_mail_failed, so the reason reaches the log without any special path.
  • Sender forcing happens twice, on purpose: wp_mail_from / wp_mail_from_name catch the default sender before PHPMailer validates it (a host with no dot in its name produces wordpress@localhost, which PHPMailer rejects outright), and phpmailer_init catches the case where a caller set its own From header.

Tables#

Table Holds
{prefix}mailhouse_subscribers One row per address. manage_key is the unsubscribe token; confirm_key is cleared on confirmation. revision counts changes to who the subscriber is and where they stand — see Watching the list change.
{prefix}mailhouse_tags Tags.
{prefix}mailhouse_subscriber_tags Pivot, primary key on both columns.
{prefix}mailhouse_queue One row per recipient per campaign. Unique on (campaign_id, subscriber_id) — that key is what makes a double-click on Send harmless. Rows stay after sending and carry the open and click counts, and the id the transport gave the message. claim_token and claimed_at mark a row a batch has taken; remote_job_id and reported are reserved.
{prefix}mailhouse_log One row per wp_mail() call.

Every timestamp is UTC. mailhouse_date() converts on the way out.

Schema changes apply themselves on the next request of any kind. Mailhouse_Install::maybe_install() runs on init at priority 0, ahead of the webhook and tracking handlers, and costs one read of an autoloaded option once the schema is current. It used to run on admin_init only, which a background auto-update never reaches: on a site nobody logs in to, new code would have run against old tables indefinitely. Two requests arriving together do not both run it.

mailhouse_webhook_events Normalised events parsed from a callback array $events, string $provider, array $payload

Watching the list change#

Until 1.6.0 about half the ways a subscriber could change fired nothing: an administrator editing an address, somebody correcting their own name, any change of tags. Every write now goes through one of a few functions, and each of those says what it did.

Mailhouse_Subscribers::update() compares what it is asked to write with what is stored. When one of the columns in Mailhouse_Subscribers::SYNCED actually differs — email, first_name, last_name, fields, status, source, created_at, confirmed_at, unsubscribed_at — it adds one to the row's revision and fires mailhouse_subscriber_updated with the row after, the row before, and the names of the columns that changed:

add_action(
    'mailhouse_subscriber_updated',
    function ( $after, $before, $changed ) {
        if ( in_array( 'email', $changed, true ) ) {
            // $before->email became $after->email.
        }
    },
    10,
    3
);

It does not fire for the sent, opens, clicks and bounces counters or for the keys, and not for a write that sets a column to the value it already had. sent moves on every campaign; a listener told about each of those would hear nothing else. Custom fields are compared as data, so the same fields in a different order are not a change.

confirm(), unsubscribe() and mark_bounced() all write through update(), so each fires mailhouse_subscriber_updated first and its own hook after.

revision is the cheap way to ask whether two copies of a row are the same. It moves on the changes above and on a change to the subscriber's tags, and on nothing else.

Tags. attach(), detach() and set() work out what really changed and fire mailhouse_subscriber_tags_changed once, with the ids added and the ids removed. Attaching a tag somebody already has is not a change and fires nothing. set() writes only the difference — it used to remove every tag and add them back, which reset each added_at and could leave somebody with no tags if it stopped half-way. Deleting a tag fires mailhouse_tag_deleted once with everybody who held it, not once per holder.

Deleting. mailhouse_subscribers_deleting fires before the rows go, carrying them. They are keyed by subscriber id rather than listed, and not only for convenience: do_action() unwraps a one-element list that holds an object, so a plain list would arrive as a bare row whenever exactly one subscriber was deleted.

Changing a status. Two functions, for the two cases where it is not the subscriber's own click doing it:

// An administrator's decision. Leaving the list goes through unsubscribe()
// or mark_bounced(), so the date is recorded, queued mail is dropped and the
// usual hooks fire. Joining it does not fire `mailhouse_subscriber_confirmed`,
// so a correction made in the admin sends nobody a welcome email.
Mailhouse_Subscribers::set_status( $subscriber, 'unsubscribed', 'admin' );

// The owner of the address, from their own preferences page. The only thing
// that may undo an opt-out. A bounced address cannot bring itself back.
Mailhouse_Subscribers::resubscribe( $subscriber, 'owner' );

The edit form under Subscribers uses the first. Before 1.6.0 it wrote the status column directly, so an administrator unsubscribing somebody there set no date, cleared nothing from the queue and told nobody.

Adding a transport#

Extend Mailhouse_Provider and register the class:

class Acme_Mailer extends Mailhouse_Provider {

    public function id() {
        return 'acme';
    }

    public function label() {
        return 'Acme Mail';
    }

    public function fields() {
        return array(
            'acme_key' => array(
                'label'    => 'API key',
                'type'     => 'password',
                'required' => true,
            ),
        );
    }

    public function send( $mail ) {
        $response = $this->request(
            'https://api.acme.test/send',
            array(
                'headers' => array( 'Content-Type' => 'application/json' ),
                'body'    => wp_json_encode(
                    array(
                        'from'    => $mail->From,
                        'to'      => wp_list_pluck( $this->to( $mail ), 'email' ),
                        'subject' => $mail->Subject,
                        'html'    => $this->html( $mail ),
                        'text'    => $this->text( $mail ),
                    )
                ),
            )
        );

        if ( $response['code'] < 200 || $response['code'] > 299 ) {
            $this->fail_response( $response );  // throws
        }

        return true;
    }
}

add_filter( 'mailhouse_providers', function ( $classes ) {
    $classes[] = 'Acme_Mailer';
    return $classes;
} );

The base class gives you to(), cc(), bcc(), reply_to(), html(), text(), attachments() and custom_headers(), all normalised out of the PHPMailer object, plus request() and fail_response(). A field named in fields() is rendered, sanitised and — for password fields — encrypted automatically, and picks up MAILHOUSE_ACME_KEY from wp-config.php if it is defined.

Two things are worth adding once it sends. Neither is required: a transport with neither is treated as accepting on true and as ambiguous when it throws.

// What the provider called the message. `request()` keeps its last answer,
// and `response_value()` / `response_header()` read from it.
public function message_id() {
    return $this->response_value( array( 'id' ) );
}

Failures are sorted for you when they go through request() and fail() or fail_response(): see What a send tells you.

Bounce callbacks#

?mailhouse_webhook=<provider>&k=<secret> — a query-string endpoint rather than a pretty URL, so it needs no rewrite rules and cannot break on a site with plain permalinks or one whose rules were never flushed. The secret may also travel as an X-Mailhouse-Key header, which keeps it out of access logs.

Everything arriving there is untrusted input from the public internet, so two things guard it:

  1. The URL secret, checked with hash_equals(). Every provider can carry it.
  2. A signature over the body, where the provider offers one — HMAC-SHA256 for Mailgun (over its own timestamp and token) and Resend (Svix: id, timestamp and body), ECDSA-SHA256 for SendGrid. Signed callbacks are also checked against a 15-minute clock skew, so a captured callback cannot be replayed for ever.

Verification is skipped when no key is configured for that provider, because Brevo and Postmark have no signing scheme at all and refusing them would mean no bounce handling for those two. Where a key is set, an unsigned or badly signed callback is refused outright.

Each provider's payload is normalised to a list of array( 'email', 'type', 'reason', 'message_id', 'event_id', 'occurred_at' ), where type is one of hard, soft, complaint, unsubscribe or delivered. The last three say which message and which notification this is, where the provider says: message_id is the id the send call returned, event_id is the provider's own id for the callback, and occurred_at is a Unix time. They are empty or zero when the provider does not supply them. Nothing acts on them yet — they are carried so that a bounce can be matched to the message that bounced. Anything else — opens, clicks, deferrals, processed notices — is dropped at the parser, because acting on it either duplicates our own tracking or punishes an address for a condition the provider is still retrying.

Mailhouse_Webhooks::process( $provider, $body ) does the verifying, parsing and applying and returns counts or a WP_Error; handle() is only the request plumbing around it. That split is what makes the parsers testable without a network, and it is how one of the transports without a parser yet — SES, Mailjet, SparkPost, SMTP2GO, Elastic Email, MailerSend, ZeptoMail, Mailchimp Transactional — can be bolted on: point its callback at any provider id and rewrite the events with mailhouse_webhook_events.

Repeats are no-ops. Providers retry callbacks they could not deliver, and some send the same event twice regardless, so each branch stops when the subscriber is already in the state the event describes — otherwise a fortnight of retries inflates the bounce counter and fills the log with copies of one bounce.

active_providers() reports the transports actually in use, across both the site and campaign streams, which is what the settings screen and the status report are built from.

Theme colours#

Mailhouse_Palette::detect() returns the email colours the active theme implies, as setting keys to hex. It is used in two places: the "Use my theme's colours" button, and seed_defaults() on a fresh install. Never on upgrade -- changing the look of a site's email behind its back is worse than a mismatch it has already accepted.

Two things make the result trustworthy rather than merely plausible:

  • Only what the theme declares. wp_theme_has_theme_json() gates the whole thing, and only the theme and custom palette tiers are read. WordPress ships a default palette of its own, and presenting that as the theme's would be a lie.
  • Core's own styles are filtered out. wp_get_global_styles() merges the theme with core's theme.json, which declares a literal button background of #32373c and nothing for page background, text or links. So a literal is trusted for those three, while the button is accepted only when it resolves through the theme's own palette -- otherwise every site would get core's grey wearing the theme's name. There is a test for exactly that.

Values arrive as a literal hex, as var:preset|color|slug, or as the CSS custom property that form compiles to; all three are resolved against the palette. Named colours and rgb() are left unfilled rather than guessed at.

mailhouse_shade_colour( $hex, $amount ) moves a colour toward white or black depending on its own lightness, which is what separates the message card from the page on a dark brand. mailhouse_contrast_colour( $hex ) picks black or white text for a background.

The post-click popup#

Mailhouse_Notice prints a message into wp_footer when the request carries ?mailhouse_notice=<key>, where the key names one of a fixed server-side set. An unrecognised key prints nothing at all, so the argument cannot be used to put words on the site.

It is a real element, not something a script builds: mail clients open links in all sorts of browsers, and a confirmation nobody can see because a script did not run is worse than a plain page. The stylesheet and script load only on a request that shows one. JavaScript adds closing in place, Escape, and clearing the query argument with replaceState so a refresh does not replay it.

Colours come from the email design -- surface, ink, brand -- passed as custom properties on the element, so the popup matches the site rather than following the reader's dark-mode preference into a white card on a dark site.

One palette for the front end#

mailhouse_brand_palette() is where the emails, the popup and the standalone pages get their colours. It reads template_accent, template_card_bg and template_ink, falls back on any that is not a usable hex, and derives the rest:

Slot What it is
accent, surface, ink Straight from the design
on_accent Black or white, whichever reads on the accent
muted The ink, softened, for secondary text
edge The surface, shifted, for borders that have to show against it
field The surface, barely shifted, for inputs and notices
is_dark Whether the design is dark

It exists because the three surfaces each used to work their colours out separately, and the standalone pages lost. They were written when there was only a brand colour to read, took template_accent and hardcoded white for everything else, and never caught up when the message background and text colours arrived in 1.3.0 -- so a dark design produced a dark email, a dark popup and a white preferences page. One function decides now.

is_dark is in there because the right answer to prefers-color-scheme depends on the design. A site that has chosen a dark design should stay dark whatever the reader's browser asks for -- that is the rule the emails already followed, and the popup's reason for ignoring the preference outright. A site still on the light default keeps following the reader, which is what the standalone pages have always done. Callers need to know which they are looking at, so Mailhouse_Optin::page_html() emits the dark-mode block only for a light design, and sets color-scheme to match either way.

What a send tells you#

Mailhouse_Mailer::send() returns true when the transport took the message and false otherwise, as it always has. false covers two very different things, though: the server said no, and the connection dropped and nobody knows. The first is safe to try again. The second may already be in somebody's inbox.

$sent   = Mailhouse_Mailer::send( $to, $subject, $html );
$result = Mailhouse_Mailer::last_result();

// array(
//     'outcome'    => 'accepted' | 'rejected' | 'ambiguous',
//     'permanent'  => bool,     // rejected only: trying again will not help
//     'message_id' => string,   // accepted only: the transport's id, if it gave one
//     'error'      => string,
// )

The rule every transport follows: a failure is a rejection only when it can be shown the message never left. Everything else is ambiguous.

What happened Outcome
SMTP 250 after the body; a 2xx from an API accepted
The message could not be built — no valid recipient, say rejected, permanent
API 4xx; a refusal inside a 200; SMTP 5xx rejected, permanent
API 408, 425, 429, 503; SMTP 4xx; could not connect, resolve or authenticate rejected, worth retrying
Any other API 5xx; a timeout or reset after the request was written; the line going dead after an SMTP body was sent ambiguous

The queue records message_id on the row it sent (provider_message_id). What it does with a failure has not changed: it retries, up to three times.

'no_fallback' => true keeps the backup transport out of one message. Sending again through a second route after an unclear failure on the first is how one person gets two copies; pass it wherever that matters more than getting the message out.

How the queue takes its work#

Mailhouse_Queue::claim( $limit ) takes rows with one UPDATE that marks them sending and stamps them with a token, then reads back the rows carrying that token. The database guarantees two runs arriving together come away with different rows. Before 1.6.0 the rows were read and nothing was marked; only a transient stood between two runs and the same batch, and a transient is a check followed by a write with a gap between them.

It also means a row says sending before anything is handed to a transport. A run that dies part-way leaves rows that say so; reap_stale() returns them to pending after ten minutes, which is what became of them before claims existed. Rows a batch claimed and did not reach inside its time budget are handed straight back by release().

The transient is still there. It keeps the pace to one batch a minute, which is what "emails per minute" in the settings promises; it is no longer what stops a message going twice.

Updates#

Mailhouse is not on the wordpress.org directory, so it answers for its own updates. The whole mechanism is one header and one filter.

The header matters more than it looks:

 * Update URI: https://github.com/estuty/mailhouse

Without it, WordPress asks wordpress.org about every plugin whose folder name it recognises — and a plugin installed from a zip has no way of saying where it came from. Anybody publishing a plugin under the slug mailhouse would have had it offered as an update to this one, and installing that would have overwritten it. Declaring the header both stops WordPress asking wordpress.org and routes the question to update_plugins_github.com instead, the filter added in WordPress 5.8 and keyed on the header's host.

That key is a host, not a plugin, so every plugin on the site that updates from github.com arrives at the same filter. Mailhouse_Updater::offer() therefore checks the basename it was asked about before answering — returning our release for somebody else's plugin would have WordPress install Mailhouse straight over the top of it.

Two things are deliberate:

  • The version comparison is left to WordPress. offer() reports the latest release whether or not it is newer; core files it under response or no_update itself. A filter that stayed quiet when the site was current would also lose the "View details" link.
  • The release asset is required, and the source archive is never used. GitHub's zipball_url unpacks to a folder named after the repository and the commit. WordPress installs a plugin into whatever folder the zip contains, so that would land beside the existing copy as a second plugin rather than replacing it. A release with no mailhouse-<version>.zip on it offers nothing, which is the better failure.

The answer is cached in a site transient for 12 hours, and a failed lookup is cached for 15 minutes so a renamed repository or a rate limit is not re-asked on every row of the Plugins screen. Mailhouse_Updater::status() reads that cache without ever making a request, which is what Tools → Status shows.

Point it elsewhere with MAILHOUSE_UPDATE_REPO in wp-config.php or the mailhouse_update_repo filter. The repository has to be public: GitHub answers 404, not 403, for a private one, so the symptom is simply no updates.

Cutting a release#

.github/workflows/release.yml does the packaging, because the asset is load-bearing and forgetting it is silent — a release with no zip on it offers nothing to anybody, and looks exactly like a release that reached everybody.

Push a v* tag and it builds mailhouse-<version>.zip and attaches it. If no release exists yet it opens a draft with the zip already on it, which keeps the release out of releases/latest until the notes are written; publishing it fires the workflow again, which finds the asset and checks it against the tag rather than replacing it. workflow_dispatch re-runs it for any existing tag, and its force input re-uploads.

It refuses to package a few things:

Refused Why
A tag that is not vMAJOR.MINOR.PATCH the tag is the version every site compares against
The tag, the Version: header, MAILHOUSE_VERSION and readme.txt's stable tag disagreeing a tag ahead of the header is the expensive one: core installs the update, reads the old version back out of the header, and offers the same update again, for ever
A missing or non-github.com Update URI without it the question goes to wordpress.org
A PHP file that does not parse cheap to check on the way past
A zip whose root is not a single mailhouse/ holding that version WordPress installs a plugin into whatever folder the zip contains

Two settings are pinned on the archive, and neither is decoration:

git -c core.autocrlf=false -c core.eol=lf archive --format=zip -6 --prefix=mailhouse/ "$TAG"

git archive applies line-ending conversion, and Git for Windows ships core.autocrlf=true in its system config — so the same tag archived from a fresh Windows clone comes out CRLF and 1.6KB larger than from a clone with it turned off. -6 is git's default compression, pinned for the same reason. With all three fixed the tag decides the bytes: rebuilding v1.4.0 this way reproduces the published asset's sha256 exactly.

That reproducibility is what the verify path leans on. Where the asset is already attached, the workflow downloads it and diffs .github/zip-manifest.php output — every entry's name, CRC and size — instead of hashing the file, because git archive stamps the commit date as each entry's mtime and the commit sha as the archive comment. Two archives of identical trees therefore differ in bytes while their contents do not.

The tag is checked out under src/, separately from the workflow's own checkout, so the helpers are always the ones from the ref that started the run rather than whatever happened to be in the tree being packaged — otherwise it could only ever build tags new enough to contain it.

Tests#

Eight scripts under tests/, run against a real WordPress rather than mocks — the things worth checking here are dbDelta actually creating the tables, a rewrite rule actually matching, and PHPMailer actually assembling a message, all of which a mock would get wrong.

php tests/test-core.php      # activation, settings, list, queue, transports
php tests/test-admin.php     # every admin screen, and the form endpoint
php tests/test-import.php    # CSV, Noptin and WP Mail SMTP importers
php tests/test-features.php  # transports, design, digests
php tests/test-webhooks.php  # bounce parsing and signature verification
php tests/test-branding.php  # theme colours, the design, the popup
php tests/test-updates.php   # the update check, start to finish
php tests/test-foundations.php  # change hooks, revisions, the queue claim, send results

test-foundations.php includes a race: two PHP processes started on the same tick, each claiming rows seven at a time out of five hundred until none are left. It asserts no row was claimed twice and none was missed. Five rounds by default; MAILHOUSE_CLAIM_ROUNDS=50 for a longer look. The same race run against a read-then-mark claim loses rows to both processes within a round or two, which is how the test is known to be able to fail.

test-updates.php stands in for GitHub with pre_http_request rather than calling it, so the shapes worth worrying about — a release with no zip, a renamed repository, a rate limit — can each be put in front of the code on demand. What is real is WordPress: it runs wp_update_plugins() and reads the transient core wrote, because the question being asked is whether core accepts what the filter hands it.

tests/bootstrap.php walks up from the plugin folder looking for wp-load.php; set MAILHOUSE_WP_ROOT to point it somewhere else. Each script cleans up after itself and exits non-zero on failure, so they drop into CI as they are.

They activate the plugin and write real rows. Run them on a development site, not a live one.

test-admin.php fails on any PHP notice or warning raised inside the plugin while a screen renders, which is the cheapest way to catch the class of bug that only shows up on a screen nobody opened during development.

Things deliberately not done#

  • No IMAP bounce polling. Bounces come from provider callbacks, which means an SMTP-only site gets none. Reading a bounce mailbox over IMAP would cover that case, and parsing arbitrary DSNs reliably is a project of its own.
  • No callback parsers for every transport yet. Five of them report bounces: SendGrid, Mailgun, Brevo, Postmark and Resend. The rest send a different shape, and each needs its own parser.
  • No A/B testing, no automation trees. Three automations cover what most sites need; the rest is a different product.
  • No block editor for emails. Block markup carries layout CSS that mail clients discard, and several blocks render as nothing in Outlook.
  • No REST API. The queue is internal, and exposing a subscriber list over REST is a liability rather than a feature.
